A Real Fourier Alternative
to Kronecker Embeddings

What is a REAL Fourier alternative of Kronecker? Why can't I represent each character like a fourier wave, and just add them to make a word!!

Because a sum doesn't care about order. listen and silent come out byte-identical. Binding each byte's wave to its position by a phase rotation is the minimal repair — and the repaired code carries the same information as the shipped 8,192-dimensional grid in 2,048 dimensions.

Read both stats above, in that order. The two comparisons point opposite ways and both are real. Matched on quality, phase binding is four times cheaper. Matched on parameters, the sparse grid wins by 3.43%. The resolution is in section 03: the phase code saturates the vocabulary's ~1,400 intrinsic directions at 2,048 dimensions, so an 8,192-dim phase arm is four times past its own operating point — but that is not a complete excuse, because at equal parameters the grid's sparsity still buys something we had characterised purely as waste.

01 — The finding that reframed everything

Both codes carry the same information. One charges four times as much for it.

The obvious hypothesis was that the one-hot grid is low-rank and a dense wave code is full-rank. That is not what the vocabulary says. Measured over 10,000 randomly sampled tokens, all four codecs land on roughly the same effective rank — about 1,550 independent directions. That number is a property of the data: the byte content of this vocabulary simply spans ~1,550 dimensions, and every scheme saturates it.

So the difference isn't capacity. It's the bill.

02 — Why "just add them" cannot work

A sum has no memory of order

Assign each byte value a wave and add them up, and any two tokens that are anagrams produce identical codes. No projection layered on top can separate them, because it is never shown a difference. This is not an implementation detail to be tuned away — it is a proof that the literal reading of the problem fails, and it is what makes the repair meaningful.

On 8,000 real vocabulary tokens, naive summation merges 197 of them. Phase binding merges none. In a trained model the order-blind arm is 1.83% worse — order-blindness is not a rounding error, it collapses the representation by an order of magnitude.

03 — The trained ablation

Six arms, 40M tokens each, one variable

A 512-wide, 8-layer decoder. Architecture, optimiser, schedule, seed and the token stream itself are pinned across arms; the embedding module is the only thing that differs. Metric is bits-per-byte, which is comparable across languages where per-token loss is not.

04 — Invertibility

The code decodes back to its own bytes, and tolerates being wrong

Unbind a position by multiplying by its conjugate atom, then take the argmax correlation over the 256 byte atoms. The argmax over a known finite alphabet is the cleanup step that lifts approximate retrieval to exact recovery. This matters beyond elegance: the stated blocker on making Kronecker reversible is that "the neural network does not predict exactly those numbers we want." A redundant phase code is an error-correcting code.

05 — What we got wrong

The predictions that didn't survive contact

"Six thousand dead projection rows." An early draft claimed the unreachable grid cells were parameters that could never receive gradient. True of the raw code, false of the shipped one — the codec z-normalises, so never-activated cells map to −mean/std, not zero. The ablation harness printed dead rows 0 of 8,192 and caught it. The structural waste is real; "dead" was the wrong test, and effective rank is the right one.
"More code dimensions will help." fourier_8192 was meant to be the strongest structured arm and is the weakest, at +3.43% — and it is the arm that loses the parameter-matched head-to-head. Redundancy explains part of it: 8,192 coordinates carrying ~1,400 directions means four times the projection parameters to fit from the same 40M tokens. But redundancy cannot be the whole explanation, because kronecker_32 carries ~1,385 directions in the same 8,192 dimensions with the same parameter count and does better. The remaining difference is sparse versus dense activation: the grid lights ≤32 of 8,192 rows per token, so each row trains like a lookup entry, while the phase projection must unmix a dense random mixture. An earlier draft stopped at "redundancy", which explains the comparison against fourier_2048 and silently skips the one that matters.
Every arm is one seed. Seed variance was never measured, so the 0.12% fourier_2048 / kronecker_32 gap is almost certainly inside noise. "Parity" is a defensible reading of it; a win would not be. Three runs that would settle the open questions — a seed sweep, a 512/1024-dim sweep to trace the efficiency frontier rather than sample two points on it, and a sparsified phase code at 8,192 dims to isolate the sparsity confound — are about five GPU-hours and have not been run.
"Long tokens are where the crop loses." They aren't, at this scale. On targets over 32 bytes the two codes tie within a wide error bar (382 / 149 / 157 scored positions). The 559 over-long tokens are 0.8% of the vocabulary — too rare to move a corpus-level metric.
Bonus: widening the window doesn't help either. kronecker_48 removes every collision in the vocabulary and trains 0.59% worse than the 32-byte version, for 50% more parameters — and it is marginally worse even on the long tokens the wider window exists to serve. The session proposes this as the remedy; on this evidence the collisions it fixes are too rare to matter while the coordinates it adds still have to be trained.

One more correction worth stating plainly: the session calls the 32-byte window "the sovereign risk in the technique." Measured across the whole vocabulary it affects 22 tokens — 0.03%. Every one is Indic and none is Latin, so the direction of the claim is exactly right; the magnitude is not. At pos_dim = 16 it would be 20.6%, so 32 sits just past a cliff rather than on one.

Measured on the frozen 68,096-token sarvam1 vocabulary carried since Session 2. Static claims reproduce on a CPU in ~25 minutes with no network; the ablation ran six arms on a single T4 in about three GPU-hours. Code, proofs, tests and the full five-problem analysis are in the repository.
